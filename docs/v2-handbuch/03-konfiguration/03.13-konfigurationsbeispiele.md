# 03.13 – Konfigurationsbeispiele

Vier Betriebssituationen, vier Konfigurationsentwürfe: Realtime-Kette, Wake-Word-Installation, Multiuser-Server, CPU-Konfiguration. Alle Werte aus `config.yaml` oder Klassendefaults des Commits `a8993c5c68042d996eab680d84a5b138a214bb5d`. **Beispielwerte**, keine Messungen, keine Betriebsempfehlungen: *wie* man eine Absicht in startfähige Konfiguration übersetzt und *wann* Werte wirken – nicht, welche Zahlen am besten sind.

## 1. Worum geht es?

Die Kapitel davor erklären das System: Typen/Validierung ([03.04](./03.04-datentypen-und-validierung.md)), Einzelbedeutung ([03.06](./03.06-server-einstellungen.md), [03.07](./03.07-session-einstellungen.md)), Wirksamkeitszeitpunkt ([03.09](./03.09-wirksamkeitszeitpunkt.md)), Abhängigkeiten ([03.12](./03.12-abhaengigkeiten.md)). Hier vier zusammenhängende Entwürfe.

Jeder Entwurf = vollständiger `settings`-Abschnitt mit `version: 1`. Startfähig, wenn Server via `--config` lädt ohne abzubrechen – und Modelle bereits vorhanden (keine Beschaffung hier).

Zwei Regeln, was überhaupt drinstehen darf:

1. **Kein freies Namensverzeichnis.** `settings:` mappt 1:1 auf `ServerSettings`-Felder. Unbekannt/Secret/abgeleiteter Pfad → `SystemExit`. `device` nur `cpu` (X1-02).
2. **Typ entscheidet Schreibweise.** `wake_words` = einzelner Komma-String (keine Liste); Float nimmt int/float, kein bool; Dict nur Objekt/`null` (X1-03).

Abgrenzung – bewusst NICHT startfähig:

```yaml
# Bewusst NICHT startfähig – nur zur Abschreckung
version: 1
settings:
  wakeWord:
    sensitivity: 0.5     # kein ServerSettings-Feld
  cpu_threads: 4         # gehört nach deployment:
  admin_api_key: "..."   # Secrets gehören in die Env-Datei
```

Bereits der erste Name beendet den Start. Beispiele halten sich strikt an die Allowlist (X1-02).

## 2. Das Wesentliche auf einen Blick

### 2.1 Fünf Startregeln

| # | Regel | Bedeutung | Beleg |
|---|---|---|---|
| 1 | `version: 1` + `settings:`-Objekt | Andere Version → Abbruch; nur dieses Objekt gelesen | X1-02 |
| 2 | Nur `ServerSettings`-Felder | Unbekannt → `SystemExit`, keine Warnung | X1-02 |
| 3 | Keine Secrets/Abgeleiteten Pfade | Zugangsdaten → Env ([03.11](./03.11-secrets.md)); Pfade aus `data_root_path` | X1-02 |
| 4 | `device: cpu` | Anderes → `SystemExit`; Installation CPU-only | X1-02 |
| 5 | Typgerechte Schreibweise | Komma-String, kein `bool` für Zahlen, Dict nur Objekt/`null` | X1-03 |

`tuning_profile` nur `custom`; keine Presets – Batch/Timing/VAD explizit (X1-06). YAML = CLI-Defaults; explizites CLI überschreibt; `None`-Felder fallen auf YAML/Basis zurück (X1-05).

### 2.2 Drei Wirksamkeitsklassen

| Klasse | Bedeutung | Beispiel |
|---|---|---|
| `ACTIVE` | live aus laufenden Settings gelesen | `max_sessions`, `max_realtime_queue_age_ms` |
| `NEW_SESSION` | beim Aufbau kopiert | `realtime_processing_pause`, `pre_recording_buffer_duration` |
| `STARTUP_ONLY` | Live-Patch abgewiesen (`startup_only`); nur Neustart | `model`, `compute_type` |

Ausnahmen beachten (Abschnitt 7): Manche Label lügen faktisch (C-01, C-03). Immer Label **und** belegte Wirkung lesen.

### 2.3 Lesart der Tabellen

Spalten: **Feld · Wert · Beleg** (YAML-Zeile + Fakten-ID) **· Klasse**. Beleg nennt die Quelle: `config.yaml` = versionierte Datei, `ServerSettings` = Klassendefault. Nötig, weil Datei an mehreren Stellen abweicht (C-04). Keine Rangliste.

## 3. Beispiel A – Realtime

Referenzkonfiguration, keine Mess-/Laufzeitaussage: großes Final-Modell (Faster-Whisper), separates Streaming-Modell (Kroko-ONNX), Timing-/Pufferkanten.

```yaml
version: 1
settings:
  device: cpu
  language: de
  tuning_profile: custom
  transcription_engine: faster_whisper
  model: faster-whisper-large-v3-turbo
  realtime_transcription_engine: kroko_onnx
  realtime_model: Kroko-DE-Community-64-L-Streaming-001.data
  use_main_model_for_realtime: false
  realtime_processing_pause: 0.02
  realtime_batch_size: 16
  batch_size: 16
  beam_size_realtime: 3
  vad_filter: true
  realtime_callback: update
  early_transcription_on_silence: 0.2
  pre_recording_buffer_duration: 0.75
  max_realtime_queue_age_ms: 1500
```

| `transcription_engine` | `faster_whisper` | `config.yaml:16` · X1-07 | `STARTUP_ONLY` |
| `model` | `faster-whisper-large-v3-turbo` | `config.yaml:17` · X1-07 | `STARTUP_ONLY` |

| `realtime_batch_size` | `16` | `config.yaml:44` · X1-07 | `NEW_SESSION` (Label), faktisch `STARTUP_ONLY` (C-01) |

`use_main_model_for_realtime: false` = strukturbestimmend: zwei Lanes/Queues/Worker (`balanced-main-plus-realtime`); Gegenstück `low-memory-one-model` (X1-11). Zwei Engines/Modelle im Speicher, Speicherprüfung bewertet Paarung (Abschnitt 6 „Idle-Unload + Speicherpolitik“).

`realtime_processing_pause: 0.02` = Schleifentakt nach Intervallsablauf (X1-08). `early_transcription_on_silence: 0.2` = echte Recorder-Früh-Transkription nach 0,2 s Stille vor Turnende (X1-09). `realtime_callback: update` wählt Update-Kanal (`stabilized` = anderer Kanal, X1-10). `pre_recording_buffer_duration: 0.75` = Vorlaufpuffer mit Audio bei Aufnahmestart (X1-07).

`max_realtime_queue_age_ms: 1500` anders: Deadline beim Einreihen; überschritten beim Auswählen → verworfen (X1-21, X1-24). Live gelesen, gilt für neu eingereihte Jobs ohne neue Session.

### 0,0-Falle

`realtime_processing_pause: 0.0` typzulässig, aber auf min. `0.001` geclampt: aus 0,0 wird 0,001, nicht 0; ungültig → 0.2 (X1-08). „Aus“ nicht ausdrückbar – positive Zahl setzen. Gegenfall: `max_audio_queue_seconds_per_session: 0` schaltet Dauerbegrenzung tatsächlich ab (Sample-Grenze nicht positiv, X1-23). Zwei Nullen, zwei Bedeutungen – Implementierung lesen, nicht Namen (X1-08, X1-23).

### Haken `realtime_batch_size`/`vad_filter`

Beide `NEW_SESSION`-gelabelt, faktisch `STARTUP_ONLY`: V2-Sessions nutzen externe Executoren, Recorder baut keine Engines; Werte fließen in geteilten Engine-Aufbau des Schedulers (X1-26). Live-Patch ändert nicht Versprochenes. Vollständig: C-01 in §7.3.

## 4. Beispiel B – Wake-Word

```yaml

settings:
  device: cpu
  wakeword_backend: openwakeword
  wake_words: hey_jarvis
  openwakeword_model_paths: hey_jarvis_v0.1.onnx

  wake_word_activation_delay: 0.0

  wake_word_buffer_duration: 0.1
```

Profil nur aktiv, wenn Backend **und** Wörter nicht leer (X1-13).

### v2: Auswahl pro Session

YAML = Server-Standard. Session mit expliziter Auswahl bringt eigene IDs; Server löst einmalig gegen Katalog auf, ersetzt Backend/Wortliste/Pfade (X1-13). Ausschnitt (kein vollständiges `hello`):

```json
{
  "requestedSession": {
    "trigger": { "manual": false, "wakeWord": true },
    "wakeWordIds": ["hey_jarvis"]
  }
}
```

Admission fail-closed (X1-17): Wake ohne IDs → `wake_word_selection_required`; IDs ohne Wake → `wake_word_selection_not_allowed`; unbekannt/deaktiviert/nicht-ladbar → ganze Auswahl abgelehnt (`wake_word_unavailable`), keine Teilannahme; Katalog genau einmal befragt. Alternativ Patch `wakeWord.selection` (wirkt neue Sessions, X1-14). Vertrag: [03.08](./03.08-runtime-aenderungen.md).

### Registry-Werte, inkl. `calibration:pending`

| Schlüssel | Scope | Typ | Default | Apply | Kalibrierung |
|---|---|---|---|---|---|
| `wakeWord.selection` | Session | Liste | `[]` | `next_session` | – |
| `wakeWord.sensitivity` | Session | Float 0,0–1,0 | `0.5` | `next_activation` | – |
| `wakeWord.minConsecutivePredictionFrames` | Session | Int, min 1 | `1` | `next_activation` | `pending` (WW-18) |
| `wakeWord.cooldownMs` | Session | Int, min 0 | `0` | `next_activation` | `pending` (WW-18) |
| `wakeWord.preRollMs` | Session | Int, min 0 | `0` | `next_activation` | `pending` (WW-19) |
| `wakeWord.detectorGain` | Session | Float 0,0–3,0 | `1.0` | `next_activation` | `pending` (WW-18) |
| `wakeWord.vadThreshold` | Session | Float 0,0–1,0 | `0.0` | `next_session` | `pending` (WW-18) |
| `wakeWord.inferenceBackend` | Server/Admin | `auto`/`onnx`/`tflite` | `auto` | `next_session` | – |
| `wakeWord.globalDisabledIds` | Server/Admin | Liste | `[]` | `next_session` | – |

`pending` = vorläufiger Schutzzaun, **kein** kalibrierter Vertrag, **keine** Empfehlung (X1-15). Defaults = neutrale Startwerte; Kalibrierung (WW-18/WW-19) verlangt reale Wake-Aufnahmen, unbelegt.

`sensitivity` wirksam = Registry, eingefroren pro Versuch; Patch während Utterance erst nächsten (X1-16).

### Drei Warnungen

> **C-02 – Zwei Empfindlichkeitsebenen.** YAML = Start/Fallback; wirksam = Registry (Fallback `or 0.5`, X1-16). Nur YAML ändern ≠ wirksam ändern.

> **C-05 – `0.0` wird zu `0.5`.** Typzulässig, aber `... or 0.5` hebt auf (X1-16). YAML kann 0,0 nicht ausdrücken; Registry kennt 0,0.

> **C-06 – Backend-Namen frei, aber nicht vertraglich.** Start nimmt beliebige Strings; v2 normalisiert auf `openwakeword` (X1-13). Mit Auswahl ersetzt Admission das Feld.

## 5. Beispiel C – Multiuser

```yaml
version: 1
settings:
  device: cpu
  max_sessions: 8
  max_active_speakers: 4
  audio_queue_size: 128
  max_audio_queue_seconds_per_session: 30.0
  pre_recording_buffer_duration: 0.75
  max_realtime_queue_age_ms: 1500
  max_final_queue_depth_per_session: 8
  max_global_inference_queue_depth: 64
```

| Feld | Wert | Beleg | Klasse |
|---|---|---|---|
| `device` | `cpu` | `config.yaml:12` · X1-18 | `STARTUP_ONLY` |
| `max_sessions` | `8` | `config.yaml:71` · X1-18 | `ACTIVE` (Default `4`, C-04) |
| `max_active_speakers` | `4` | `config.yaml:72` · X1-18 | `ACTIVE` |
| `audio_queue_size` | `128` | `config.yaml:73` · X1-18 | `NEW_SESSION` (C-07) |
| `max_audio_queue_seconds_per_session` | `30.0` | `config.yaml:75` · X1-18 | `NEW_SESSION` |
| `pre_recording_buffer_duration` | `0.75` | `config.yaml:76` · X1-18 | `NEW_SESSION` |
| `max_realtime_queue_age_ms` | `1500` | `config.yaml:77` · X1-18 | `ACTIVE` |
| `max_final_queue_depth_per_session` | `8` | `config.yaml:78` · X1-18 | `ACTIVE` |
| `max_global_inference_queue_depth` | `64` | `config.yaml:79` · X1-18 | `ACTIVE` |

### Sessions vs. gleichzeitig Sprechende

`max_sessions: 8` = Admission. Reserve/add/vorab lehnen bei belegten Plätzen ab; `rejectedSessions` steigt (X1-19). Test: bei `max_sessions: 1` zweite Session `None`, aktiv 1, rejected 1.

`max_active_speakers: 4` = erst Aufnahmestart. Neuer Sprecher ignoriert, Chunks verworfen, Warnung; Zähler unverändert; Session läuft weiter (X1-20). 8 Sessions ≠ 32 Sprecher – zweite Grenze unabhängig, verhindert Aufnahme, keine Session.

### Drei Queues, ein fester Verteiler

- `max_final_queue_depth_per_session` nur finale je Session.
- `max_global_inference_queue_depth` Summe alle, final **und** Realtime.
- Realtime je Session ein Slot: neuer ersetzt alten (`coalesced`); finale nie verdrängt (X1-21).

Fest verdrahtet: Round-Robin über Sessions, je Session Final vor Realtime, stale-Realtime-Drop. Test `a → b → a` (X1-22). Fairness **nicht konfigurierbar** – nur Tiefen/Limits, kein Rotations-Schalter (N7).

### Ähnliche Namen, verschiedene Wirkung

`max_audio_queue_seconds_per_session: 30.0` Dauer → Force-Finalize (X1-23). `audio_queue_size: 128` als `allowed_latency_limit` in **Chunk-Anzahl**: darüber alte Chunks verworfen (X1-23, C-07). Dauer vs. Rückstau – nicht Sessions/Durchsatz.

### Live oder Aufbau

Queue-Grenzen/Store/Deadlines live gelesen (X1-24). `audio_queue_size`, 30-s-Grenze, Pre-Buffer beim Aufbau kopiert (X1-24). Live-`max_sessions` wirkt sofort; Live-`audio_queue_size` nur neue Recorder.

### Threads stehen nicht in `settings`

Thread-Zahl = Deployment: `deployment.cpu_threads` → `VOICESTT_CPU_THREADS` → `OMP_NUM_THREADS` (X1-30). Unter `settings:` unbekannt → Abbruch (X1-02). Engine-Ebene: `transcription_engine_options`/`realtime_transcription_engine_options` mit `cpu_threads`/`num_workers`; Realtime erbt Final bei `null` (X1-30). Kein Server-CLI-Flag.

### Ein Engine-Aufbau für alle

`compute_type`/Beam/Batch/VAD → **ein** geteilter Scheduler-Engine-Aufbau, nicht Session-Engines. V2-Sessions nutzen externe Executoren, Recorder baut keine (X1-26). Darum faktisch Start-wirksam trotz anderer Labels.

`model_warmup: false` doppelt: Engine-Warmup mit Datei + `warmup_vad` je Recorder (X1-27). API `STARTUP_ONLY`, VAD-Anteil `NEW_SESSION`.

### Idle-Unload + Speicherpolitik

Intervall `min(30, max(0.1, timeout/4))`; bei 3600 s → 30 s. Entladen nur ohne Sprecher/Arbeit; Request lädt nach. Verschoben bei Arbeit, kein Fehler (X1-28). Echter Live-Hebel.

Ränge: kroko 2, large-v3-turbo 3 (Medium), medium 3, large 4, small 2, base/tiny 1 (X1-29). Medium-Limit 2 bei true, sonst 1; Rang 4 immer abgelehnt. Hier: nur Turbo Medium → Start ok. Verstoß an Lifecycle-Route → 400 (X1-29).

`compute_type` nicht enumeriert: `int8` Default, Alternativen unbelegt (N4). `cpu_threads: 4` Deployment-Default, keine Kalibrierung (N5) – kein Optimum behauptet.

### Dieselben Werte via CLI

YAML = Defaults; Flags setzen explizit (X1-05):

```bash
voicestt-server \
  --compute-type int8 \
  --model faster-whisper-large-v3-turbo \
  --realtime-engine kroko_onnx \
  --realtime-model Kroko-DE-Community-64-L-Streaming-001.data \
  --batch-size 16 \
  --realtime-batch-size 16 \
  --no-model-warmup \
  --model-idle-unload \
  --model-idle-timeout-seconds 3600 \
  --model-memory-policy \
  --allow-two-medium-models
```

`--no-model-warmup` = invertierte Form von `model_warmup: false`. Booleans bereits default-aktiv; je `--no-…`-Variante vorhanden. `use_main_model_for_realtime: false` ohne Gegen-Flag: `--use-main-model-for-realtime` nur `store_true`; YAML-`true` → Weglassen reicht nicht.

## 7. Grenzen

### 7.1 Deklariert, ohne Wirkung

Felder existieren, typgeprüft, veröffentlicht – kein Konsument liest sie (N1–N3). Klasse sagt, *wann* übernommen würde; ohne Konsument nichts zu übernehmen.

| ID | Feld(er) | Befund |
|---|---|---|
| N1 | `realtime_min/max_audio_seconds` | nur Feld, CLI, Veröffentlichung |
| N2 | `vad_energy_threshold` | nie an Recorder/Engine |
| N3 | `realtime_degradation_threshold_ms` | nur `limits_dict`, keine Auswertung |

### 7.2 Nicht belegt – keine Aussage

| ID | Thema | Folge für Beispiele |
|---|---|---|
| N4 | `compute_type`-Werte | nicht enumeriert; nur `int8` belegt |
| N5 | Thread-Optimum | kein Beleg; `4` Deployment-Default |
| N6 | Pause→Latenz | nur Kadenz + Clamp belegt |
| N7 | Fairness-Schalter | existiert nicht; nur Tiefen/Limits |

### 7.3 Sieben Stolperfallen

> **C-01 – Label ≠ Wirkung.** `realtime_batch_size`/`vad_filter` `NEW_SESSION`-gelabelt, faktisch `STARTUP_ONLY` (externe Executoren, kein Recorder-Enginebau, X1-26). Nicht „live“, nicht „nächste Session“.

> **C-02 – Zwei Empfindlichkeiten.** YAML = Start/Fallback; wirksam = Registry (Fallback `or 0.5`, X1-16).

> **C-03 – `ACTIVE` nur Start + Validierung.** Policy/Allow im Label, geprüft bei Start + Kandidaten (400). Kein Live-Neubewerten (X1-29).

> **C-04 – YAML ≠ Klassendefaults.** Quelle je Wert nennen:

| Feld | Klasse | `config.yaml` |
|---|---|---|
| `model` | `small` | `faster-whisper-large-v3-turbo` |
| `max_sessions` | `4` | `8` |
| `model_warmup` | `true` | `false` |
| `wake_word_timeout` | `5.0` | `7.0` |
| `wake_word_followup_window` | `0.0` | `7.0` |
| `wakeword_backend` | `""` | `openwakeword` |

> **C-05 – Aus 0,0 wird 0,5.** `... or 0.5` hebt zulässige 0,0 (X1-16). YAML kann 0,0 nicht ausdrücken; Registry kennt 0,0.

> **C-06 – Backend-Namen frei, aber unverbindlich.** Start nimmt Strings; v2 normalisiert `openwakeword` (X1-13). Auswahl ersetzt Feld.

> **C-07 – `audio_queue_size` ≠ Kapazität.** Als `allowed_latency_limit` (Chunk-Anzahl); drüber alte Chunks weg (X1-23). Rückstau, nicht Sessions/Durchsatz.
