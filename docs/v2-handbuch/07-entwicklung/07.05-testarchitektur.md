## 1. Worum geht es?

Dieses Kapitel beschreibt keine Testläufe, sondern das **Baugerüst** der Tests: wo sie liegen, welcher Art sie sind, welche Umgebung sie brauchen und welche Invarianten sie festnageln. Leitfrage: „**was passiert, wenn ich nur `pytest` tippe?**"

Antwort: Die Konfiguration besteht aus genau zwei Einstellungen: `testpaths=tests/unit` und `python_files=test_*.py` (TA7-01). Ein nacktes `pytest` sammelt damit **ausschließlich** `tests/unit` – inklusive der dort liegenden Vektor-Contract-Tests. Nur Packaging/Compatibility laufen mit explizitem Pfad; die CI nennt Pfade explizit, der Release-Candidate ruft eine Einzeldatei auf (TA7-03). Das ist die **Blanko-Falle**: grüner Standardlauf ≠ lieferbares Paket.

Zweite Falle: Ordnernamen lügen. `tests/unit` enthält auch Contract-, Integrations- und E2E-Prüfungen (TA7-11). `tests/contracts` enthält keine Tests, sondern nur Daten + README (TA7-10). Gliedere **nach Testart**, nicht nach Verzeichnis (K2). Drittens keine Marker: keine Registrierung, keine strict-Prüfung, nur `parametrize`/`skipif`/`usefixtures`; `-m slow` ist kein Weg (TA7-02, N1). Selektion geschieht über **Pfade**.

Praxis: Build-Config ändern + `pytest` → 93 Unit-Module arbeiten, 2 Packaging-Module nicht. Grün, aber Wheel ggf. kaputt. Umgekehrt prüft `pytest tests/packaging` Archive/Venvs, aber keine Protokoll-Semantik.

## 3. Sammlung und Layout (TA7-01..05)

**Minimal (TA7-01).** Nur testpaths + python_files; keine markers/addopts/pythonpath/importmode. Fehlendes (Coverage/Parallel/Retry) via Aufrufdisziplin ersetzen (N4/N5).

**Muster (TA7-04/05).** `python_files=test_*.py`: Nur test_-Präfix zählt. Wurzel-Skripte teils `*_test.py`, teils ohne Präfix – keines `test_*.py` → **nicht** gesammelt. Manuelle Helfer (venv/GUI/echte Geräte), keine Suite (TA7-05). Explizite Nennung: Pytest-Semantik, im Repo offen (U2).
