# 7. ROOT-FINDING F1 – WATCHDOG CROSS-FIELD KANN SEQUENZIELL UMGANGEN WERDEN

## 7.1 Fehler in C1

C1 `validate_timing_bundle(...)` enthält sinngemäß:

```python
if ACTIVATION_WATCHDOG_WARNING not in changes:
    return []
```

Dadurch wird die Cross-Field-Regel nur geprüft, wenn **Warning selbst** geändert wird.

Verbotener, derzeit möglicher Ablauf:

```text
Start:
warning = 30000
refresh = 180000
initial = 600000

Patch 1:
warning = 59000
→ gültig

Patch 2:
refresh = 30000
→ C1 akzeptiert fälschlich

Endzustand:
warning 59000 >= refresh 30000
→ Contract verletzt
```

Gleiches gilt beim Absenken von `segmentWatchdogInitialMs`.

## 7.2 Verbindliche Korrektur

Die Cross-Field-Prüfung wird ausgeführt, sobald **irgendeiner** dieser drei Keys Teil der Transaktion ist:

```text
activation.segmentWatchdogWarningMs
activation.segmentWatchdogInitialMs
activation.segmentWatchdogRefreshMs
```

Pseudo:

```python
WATCHDOG_CROSS_FIELD_KEYS = frozenset({
    ACTIVATION_WATCHDOG_WARNING,
    ACTIVATION_WATCHDOG_INITIAL,
    ACTIVATION_WATCHDOG_REFRESH,
})

if not WATCHDOG_CROSS_FIELD_KEYS.intersection(changes):
    return []

warning = candidate[ACTIVATION_WATCHDOG_WARNING]
initial = candidate[ACTIVATION_WATCHDOG_INITIAL]
refresh = candidate[ACTIVATION_WATCHDOG_REFRESH]

assert warning < initial
assert warning < refresh
```

Wichtig:

- Werte kommen aus dem **vollständigen finalen `candidate`**;
- nicht aus `changes`, außer der Candidate wurde zuvor bereits daraus gebaut;
- per-field Typ-/Rangevalidierung bleibt davor bestehen;
- Fehlerfeld bleibt `activation.segmentWatchdogWarningMs`;
- Code bleibt `cross_field_conflict`;
- deterministische Error-Sortierung bleibt.

Dies gilt identisch für:

```text
SessionSettingsState.apply_patch
ServerSettingsState.patch_server
```

Keine doppelte eigene Regel implementieren; beide verwenden dieselbe Helperlogik.

## 9.2 Verbindliche strukturelle Lösung

Führe **einen einzigen atomaren Admission-Read** in `SessionSettingsState` ein.

Bevorzugte Form:


```python
def activation_admission_settings(self) -> ActivationAdmissionSettings:

        revision = self._revision
```

- `effective_settings` und `timing_seconds` stammen aus **demselben gelockten Snapshot**;

```text
+ live runtimeSuppression projection

```

```text

settings_effective_for_wire separat lesen
```

## 9.3 Runtime Suppression bleibt separat live

Das ist **kein** Fehler, solange:

# 11. ROOT-FINDING F5 – PERSISTENZFEHLER ERZEUGT HALBEN SERVER-SETTINGS-COMMIT

## 11.2 Verbindliche Korrektur – PREPARE → PERSIST → COMMIT

`patch_server()` bleibt unter seinem Settingslock atomar.

Ablauf:

```text
1. aktuelle Revision prüfen
2. vollständig validieren
3. no_change prüfen
4. next_overlay als Kopie bauen
5. next_effective als Kopie bauen
6. next_revision = current_revision + 1
7. next state PERSISTIEREN
8. NUR WENN Persistenz erfolgreich:
      self._overlay = next_overlay
      self._server_effective = next_effective
      self._revision = next_revision
9. PatchResult(applied)
```

Bei Persistenzfehler:

```text
RAM unverändert
Revision unverändert
Datei unverändert
kein Success-Result
```
