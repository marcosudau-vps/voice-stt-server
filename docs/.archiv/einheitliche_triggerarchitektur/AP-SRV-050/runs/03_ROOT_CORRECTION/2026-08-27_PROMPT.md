## 2. Einziger Root-Befund

C2 mutiert bei `session_settings.patch` zuerst die `SessionSettingsState` auf Revision N+1 und spiegelt erst danach über `_bind_settings_patch()`:

```text
ProtocolSessionState.settingsRevision = N+1
settings.changed
```

Parallel baut `session.snapshot` aktuell mehrere getrennte Reads:

```text
ProtocolSessionState.settingsRevision
requestedSettings
effectiveSettings
```

Dadurch kann unter Parallelität ein Zwischenzustand sichtbar werden, z. B.:

```text
settingsRevision = N
requested/effective = N+1
```

Außerdem darf ein Domainevent, das bereits neue Settings N+1 verwendet, `settings.changed` für N+1 nicht überholen.

## 3. Verbindliche Lösung

### 3.1 Vorhandene AP-SRV-040-Wire-Grenze verwenden

Keine neue Lock-Architektur.

Verwende ausschließlich:

```python
self._event_dispatch_lock = threading.RLock()
```

als gemeinsame Wire-Linearisierungsgrenze.

### 3.2 Gesamten Settings-Patch unter diese Grenze legen

`_apply_settings_patch()` so ändern, dass dieser gesamte Block unter `_event_dispatch_lock` läuft:

```text
settings_port.patch(...)
→ _bind_settings_patch(...)
→ ProtocolSessionState.set_settings_revision(...)
→ settings.changed über bestehendes _dispatch_events()
```

Sinngemäß:

```python
def _apply_settings_patch(self, parsed):
    def apply():
        with self._event_dispatch_lock:
            patch = self.settings_port.patch(
                parsed.payload["baseSettingsRevision"],
                parsed.payload["changes"],
            )
            return self._bind_settings_patch(patch)

    return self._answer_cached(parsed, apply)
```

Minimal äquivalente Umsetzung zulässig.

`_dispatch_events()` bleibt unverändert Eventautorität.  
Der Lock ist bereits `RLock`; reentrantes Erwerben ist beabsichtigt.

Keine zweite Queue, kein Reorder-Buffer, keine zweite Settings-/Eventautorität.

### 3.3 Snapshot auf dieselbe Grenze legen

`ProtocolV2Connection._snapshot_payload()` muss den vollständigen Snapshot unter demselben `_event_dispatch_lock` bauen.

Sinngemäß:

```python
def _snapshot_payload(self):
    with self._event_dispatch_lock:
        return snapshot_layer.build_snapshot(...)
```

Damit kann kein Snapshot mitten zwischen Settings-Domaincommit und Wire-Mirror/`settings.changed` entstehen.

## 6. Snapshot-Build-Regel

Für Settingsdaten nicht mehr unabhängig lesen:

```text
state.versions()
requested_settings()
effective_settings()
```

Stattdessen:

1. `_snapshot_payload()` hält `_event_dispatch_lock`.
2. SettingsPort liefert einen atomaren Projection-Bundle-Read.
3. `settingsRevision` im Snapshot stammt aus diesem Bundle.
4. Requested/Effective stammen aus demselben Bundle unter Erhalt der bestehenden Activation-Latch-/next_session-Semantik.
5. `stateVersion` und `lastEventSeq` bleiben bei `ProtocolSessionState`.
6. Unter `_event_dispatch_lock` müssen Wire-Mirror-Revision und Projection-Revision konsistent sein.
