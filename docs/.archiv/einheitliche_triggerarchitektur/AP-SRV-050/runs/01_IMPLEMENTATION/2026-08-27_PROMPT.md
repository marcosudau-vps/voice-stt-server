# 7. VERBINDLICHE SETTINGS-DOMÄNEN

## 7.1 Sechs Activation-/Watchdog-Timings

Exakte öffentliche Keys:

```text
activation.initialSpeechTimeoutMs
activation.followupTimeoutMs
activation.segmentWatchdogInitialMs
activation.segmentWatchdogRefreshMs
activation.segmentWatchdogWarningMs
activation.closingRecoveryTimeoutMs
```

Alle:

```text
scope = session
auth = session
applyPolicy = next_activation
type = integer
```

Defaults / Constraints:

| Key | Default | Bereich |
|---|---:|---:|
| `activation.initialSpeechTimeoutMs` | 15000 | 100–3600000 |
| `activation.followupTimeoutMs` | 3000 | 100–60000 |
| `activation.segmentWatchdogInitialMs` | 600000 | 60000–3600000 |
| `activation.segmentWatchdogRefreshMs` | 180000 | 30000–600000 |
| `activation.segmentWatchdogWarningMs` | 30000 | >=5000 und strikt kleiner als jede für die Activation wirksame Watchdog-Frist |
| `activation.closingRecoveryTimeoutMs` | 5000 | 1000–30000 |

Cross-field-Validierung erfolgt gegen den **vollständigen Candidate nach Anwendung der gesamten atomaren Patch-Transaktion**, nicht feldweise gegen einen Zwischenzustand.

Für `segmentWatchdogWarningMs` bedeutet das insbesondere:

```text
warning < segmentWatchdogInitialMs
warning < segmentWatchdogRefreshMs
```

nach Auflösung der Candidate-Werte.

## 7.2 Wake-Word-Sensitivity

Verbindlich:

```text
scope = session mit Serverdefault
auth = session
type = number
constraints = 0.0 bis 1.0 inklusive
defaultValue = 0.5
applyPolicy = next_activation
```

AP-SRV-050 verwaltet und veröffentlicht Requested/Effective Value.

**Nicht** die Detectionengine aus AP-SRV-060 implementieren.
AP-SRV-060 bindet diesen Wert später an die tatsächliche Wake-Word-Inferenz.

## 7.3 Wake-Word-Auswahl

Verbindlich:

```text
scope = session
auth = session
applyPolicy = next_session
```

Sie ist atomar.

Regeln:

- wenn Wake Word für die Session konfiguriert ist, darf die Auswahl nicht leer sein;
- unbekannte IDs werden maschinenlesbar abgelehnt;
- aktuelle `WakeWordPort`-/Catalog-Capabilities dürfen zur Validierung verwendet werden;
- die aktuell laufende Session wird durch eine `next_session`-Änderung nicht umgebaut;
- `requestedValue` darf sich ändern;
- `effectiveValue` bleibt bis zur nächsten Session die tatsächlich aktuelle Auswahl.

Nicht implementieren:

```text
selected-only Modellinitialisierung
Detection-Latch
Cooldown
Pre-Roll
WakeWord-Eventaufnahme
```

Das ist AP-SRV-060.

## 7.4 Runtime-Suppression

Runtime-Suppression Manual/Wake ist bereits durch

```text
trigger_suppression.set
ActivationController.set_runtime_suppression()
```

autorisiert.

AP-SRV-050 darf sie im Registry-/Metadatenmodell **darstellen**, aber:

- kein zweiter persistierter Suppressionswert;
- keine zweite Laufzeit-State-Machine;
- keine Persistenz über App-Neustart;
- keine Änderung der vorhandenen `clientRunId`-/Reconnect-Semantik.

Der dedizierte `trigger_suppression.set`-Pfad bleibt die Runtime-Schreibautorität.

`session_settings.patch` soll Suppression **nicht zusätzlich als zweiten Write-Pfad** einführen, sofern keine der oben genannten frozen Quellen dies explizit verlangt.

## 7.5 Serverweite Trigger-/Wake-Grundlage

AP-SRV-050 führt die admin-geschützte serverseitige Registry/Persistenzgrundlage ein für die im bereits geprüften Prep-Donor vorgesehenen triggerrelevanten Serverwerte, insbesondere:

```text

Wake-Word-Sensitivity-Default
Wake-Word-Auswahl-/Katalogdefault soweit im Donor bereits vorgesehen
globale Wake-Word-Disable-IDs
```

Wichtig:

- keine vollständige Migration fachfremder Settings;
- keine neuen Cooldown-/Pre-Roll-Werte erfinden;
- globale Disable-Liste wird als Settingsgrundlage persistiert; die vollständige Wake-Katalog-/Detection-Wirkung kommt in AP-SRV-060;
- keine Modell- oder Wake-Engine neu bauen.

# 11. VERBINDLICHE TIMER-BINDING-ARCHITEKTUR

Aktuell hält `ActivationController` die sechs Timingwerte als Controllerattribute und verwendet sie direkt in `activate()`, `recording_started()`, `recording_ended()`, `refresh()` und Closing-Recovery.

Ein einfaches Mutieren dieser Attribute bei einem Settingspatch wäre **falsch**, weil eine bereits laufende Activation dann später neue Werte verwenden könnte.

## 11.1 Timingwerte pro Activation latchen

Führe eine kleine immutable Timing-Repräsentation ein, z. B.:

```python
@dataclass(frozen=True)
class ActivationTimingPolicy:
    initial_speech_timeout: float
    followup_timeout: float
    segment_watchdog_initial: float
    segment_watchdog_refresh: float
    segment_watchdog_warning: float
    closing_recovery_timeout: float
```

Der konkrete Name darf an den Code angepasst werden.

Regel:

```text
neue Activation
→ Session-Settings-Control löst aktuelle next_activation-Werte auf
→ Controller übernimmt sie genau einmal beim activate()
→ diese Activation verwendet diesen Timing-Snapshot bis Input-Close
```

Die bestehende Controller-Konstruktor-Konfiguration bleibt als Legacy-/Defaultfallback erhalten.

## 11.2 Keine rückwirkende Mutation

Patch während offener Activation:

```text
Settings-Control requested changes
Controller-current-Activation timing snapshot unchanged
```

Neue Werte werden erst beim **nächsten erfolgreichen Activation-Admission** gelatcht.

## 11.3 Manual und Wake identisch

Sowohl manual activate als auch serverinterne `wake_word`-Admission müssen dieselbe Settings-Auflösung und dieselbe Timing-Latch-Seam verwenden.

Keine getrennte Wake-Timinglogik.

# 13. REQUESTED VS EFFECTIVE – VERBINDLICHE SEMANTIK

## live

Nach akzeptiertem Patch:

```text

effectiveValue = neu
```

## next_activation

Wenn keine Activation offen ist:

```text

```

Die nächste Activation verwendet den Wert.

Wenn eine Activation offen ist:


# 14. SESSION PATCH – TRANSAKTIONSREGELN

`session_settings.patch` existiert bereits in AP-SRV-040.

Payload:

```text
baseSettingsRevision
changes
```

## 14.1 Optimistic Concurrency

Wenn `baseSettingsRevision != aktuelle Session-Settingsrevision`:

```text
accepted = false
result = settings_revision_conflict
```

mit maschinenlesbarem Error.

Keine Änderung.
Kein Event.
Kein Revision-Bump.
Kein stateVersion-Bump.

## 14.2 Atomare Validierung

Alle Changes zuerst vollständig validieren.

Wenn irgendein Key ungültig ist:

```text
result = settings_rejected
```

und:

```text
0 partielle Writes
0 Revision-Bumps
0 Events
0 Effective-Änderungen
```

Errors deterministisch nach Feld/Key sortieren.

## 14.3 no_change

Wenn alle gültigen Requested-Werte bereits identisch sind:

```text
result = no_change
accepted = true
```

und:

```text
settingsRevision unverändert
stateVersion unverändert
kein settings.changed
```

## 14.4 wirksame Transaktion

Bei mindestens einer echten Änderung:

```text
settingsRevision N → N+1
```

genau einmal für die gesamte Transaktion.

Kein Bump pro Feld.

Ack, Snapshot, SettingsPort und Event(s) zeigen dieselbe neue Revision.

# 15. MULTI-APPLY-POLICY PATCHES – HIERMIT FESTGELEGT

Eine atomare Patch-Transaktion darf Keys mit unterschiedlichen Apply-Policies enthalten.

Nicht mit einem erfundenen `applyPolicy = mixed` antworten.

Stattdessen:

1. gesamte Transaktion validieren;
2. einmal `settingsRevision` erhöhen;
3. Changed Keys nach Apply-Policy gruppieren;
4. für jede tatsächlich betroffene Apply-Policy genau ein `settings.changed` erzeugen;
5. Gruppenreihenfolge deterministisch:
   `live`, `next_activation`, `next_session`, `server_restart`;
6. `changedKeys` innerhalb jeder Gruppe lexikographisch sortieren;
7. alle Events derselben Transaktion tragen dieselbe neue `settingsRevision`;
8. die gesamte Transaktion ist **eine sichtbare Zustandsänderung**:
   - nur das erste `settings.changed` mintet mit `state_change=True`;
   - weitere Policy-Gruppen derselben Transaktion minten mit `state_change=False`;
   - damit steigt `stateVersion` genau einmal.

Logical Event Key sinngemäß:

```text
("settings.changed", settingsRevision, applyPolicy)
```

# 24. RUNTIME STORE – WRITE-PRESERVATION

Legacywrite `RuntimeConfigStore.save(settings, allowed_names)` darf nur die Legacysektion `settings` ersetzen und muss erhalten:

```text

settingsRevision
alle unbekannten kompatiblen Top-Level-Felder
```

AP-SRV-050-Controlwrite darf nur:

```text
settingsControlOverlay
settingsRevision
updatedAt
```

aktualisieren und muss die Legacysektion `settings` erhalten.

Beide schreiben weiterhin:

```text
temp file
→ os.replace
```

atomar.

# 25. RUNTIME STORE – LOCKING

Zur Laufzeit soll **eine gemeinsame RuntimeConfigStore-Instanz des Service** für Legacy- und AP050-Controlwrites verwendet werden.

Falls der Code weiterhin mehrere Instanzen auf dieselbe Datei zulässt, muss die Schreibsynchronisierung pathweit funktionieren oder eine gleichwertige Race-Sicherheit existieren.

Nicht zwei unabhängige `RLock`s verwenden, die dieselbe Datei parallel read-modify-write überschreiben können.

# 65. WICHTIGSTE REGEL

**AP-SRV-050 ist kein Metadaten-Scheinpaket.**

Die Settings-Control-Plane ist erst korrekt, wenn ein akzeptierter `next_activation`-Timingpatch nicht nur in JSON oder `effectiveSettings` auftaucht, sondern die **nächste reale Activation im AP-SRV-030-Controller tatsächlich mit genau diesem Wert läuft**, während die bereits laufende Activation unverändert bleibt.

Gleichzeitig darf AP-SRV-050 keine zweite Lifecycle-, Replay-, Event-, Suppressions- oder Wake-Word-Autorität einführen.
