## 1. Ausgangslage

W5-R01 bis W5-R03 haben eine quellcodeverwaltete Release-Zustandsmaschine unter
`release_tooling/` und einen RC-Manifest-Vertrag etabliert. Die tatsächliche
Ausführung war jedoch weiterhin an einen Operator-Rechner gebunden: der
Kroko-Artefaktspeicher, die vorgebauten Wheels und die Docker-Anmeldung lagen
lokal. Zusätzlich hat die Bestandsaufnahme dieses Runs folgende inhaltliche
Lücken gezeigt:

1. Der Git-Tag entstand erst **nach** allen öffentlichen Artefakten. Sobald
   `2.0.0` auf PyPI oder in einer Registry existiert, ist die Version aber
   bereits öffentlich belegt, ohne dass ein unveränderlicher Quellanker
   existiert.
2. GHCR wurde **vor** Docker Hub veröffentlicht, und zwar durch einen eigenen
   `docker push` eines lokalen Images statt durch Promotion desselben
   OCI-Manifests.
3. Es gab überhaupt keinen Schritt für bewegliche Aliase (`2.0`, `2`,
   `latest`).
4. Die Registry-Identitätsprüfung verglich die lokale Docker-Image-Id mit dem
   entfernten Manifest-Digest. Diese beiden Werte können nie übereinstimmen;
   jede echte Registry-Prüfung hätte damit einen Konflikt gemeldet. Das
   RC-Manifest enthielt kein Digest-Feld.
5. `fingerprint.toolchain_identity("linux")` lieferte `{"kind": "host-native"}`.
   Der Linux-Buildcontainer (`python:3.12-slim-bookworm` als bewegliches Tag,
   `apt-get update` gegen das Live-Archiv, ungepinnte pip-Werkzeuge) war damit
   kein Fingerprint-Eingang. Genau diese Lücke wurde in W4A-C3 (Finding J) für
   Windows geschlossen, für Linux aber nicht.
6. `BUILD_DATE` kam aus der Wanduhr, sodass zwei Builds derselben Quelle
   unterschiedliche Image-Identitäten erzeugten.
7. Drittanbieter-Actions waren an Tags statt an unveränderliche Commit-SHAs
   gebunden.

## 2. Ziele

1. Ein Release-Kandidat wird vollständig auf einem frischen, GitHub-gehosteten
   Linux-Runner aus einem exakten Quellcommit erzeugt.
2. Genau die qualifizierten Bytes und OCI-Manifeste werden später
   veröffentlicht, ohne Neubau.
3. Der Git-Tag existiert vor der ersten unumkehrbaren öffentlichen
   Veröffentlichung.
4. Docker Hub wird vor GHCR veröffentlicht; GHCR erhält dasselbe Manifest per
   Digest-Promotion.
5. Bewegliche Aliase werden erst nach verifizierten exakten Artefakten in
   beiden Registries gesetzt und danach selbst verifiziert.
6. Das GitHub Release ist der letzte öffentliche Erfolgsmarker.
7. Die bestehende Zustandsmaschine bleibt die einzige kanonische Autorität für
   Trockenlauf, echte Veröffentlichung und Wiederaufnahme.
8. Der öffentliche Dokumentationsstand sagt die Wahrheit: README vollständig
   neu, nur noch Faster-Whisper und Kroko-ONNX als dokumentierte
   Produktions-Engines.

## 4. Entscheidungen

### 4.1 Neue kanonische Zustandsreihenfolge

```text
PREPARED
-> TAGGED
-> PYPI_PUBLISHED
-> DOCKERHUB_PUBLISHED
-> GHCR_PUBLISHED
-> EXTERNAL_VERIFIED
-> ALIASES_PUBLISHED
-> GITHUB_RELEASED
-> FINAL_VERIFIED
-> COMPLETE
```

Die Ordnungsbarrieren werden zusätzlich defensiv in den Adaptern geprüft, damit
die Reihenfolge auch dann hält, wenn ein Adapter außer der Reihe aufgerufen
wird.

### 4.2 Kandidatenpersistenz

Wheel, sdist, Kroko-Wheels und Manifeste werden als GitHub-Actions-Artefakte
abgelegt. Die beiden Produktionsimages werden als **private** GHCR-Staging-Pakete
abgelegt und über ihren exakten Digest referenziert. Staging ist ausdrücklich
kein öffentliches Release und wird nie als solches dargestellt.

### 4.3 Freigabegrenze

Der Build-/Qualifizierungslauf und der Veröffentlichungslauf sind getrennte
Workflows. Der Veröffentlichungsworkflow ist ausschließlich per
`workflow_dispatch` erreichbar und läuft in einer GitHub-Umgebung mit
Pflichtfreigabe. Ein gewöhnlicher Push oder Pull Request kann nichts
veröffentlichen und erhält keine Release-Secrets.

### 4.4 PyPI

PyPI Trusted Publishing über GitHub-OIDC statt eines dauerhaften Tokens. Der
Schreibvorgang wird von der offiziellen PyPI-Action ausgeführt; die
Zustandsmaschine bleibt Autorität, weil der Zustandsübergang erst nach der
verifizierten Fernprüfung der exakten Dateinamen und SHA256-Werte erfolgt und
nicht durch den Exit-Code der Action.

### 4.5 Kroko-Linux-Fingerprint

Der Linux-Buildcontainer wird zur deklarierten, quellcodeverwalteten
Toolchain-Autorität (Basisimage per Digest, deklarierte apt-Paketliste,
gepinnte pip-Werkzeuge) und geht in den Linux-Fingerprint ein.
`LINUX_BUILDER_REVISION` wird von 1 auf 2 erhöht. Bereits gespeicherte
Linux-Artefakte gelten damit korrekt als nicht mehr passend. Die
Windows-Autorität und das bereits qualifizierte Windows-Artefakt bleiben
unberührt.

Ehrliche Grenze: Die exakten Debian-Paketversionen werden weiterhin gegen das
Live-Archiv aufgelöst. Diese Grenze wird dokumentiert, nicht verschwiegen; das
qualifizierte Artefakt selbst bleibt Veröffentlichungsautorität.

### 4.6 Build-Zeitstempel

`BUILD_DATE` wird aus dem Commit-Zeitstempel abgeleitet, damit ein
Wiederholungslauf derselben Quelle dieselbe Image-Identität erzeugt.

## 7. Risiken

| Risiko | Umgang |
| --- | --- |
| Fingerprintwechsel entwertet gespeicherte Linux-Artefakte | Beabsichtigt und regelkonform; der Nachweis mit leerem Speicher baut beide Varianten neu. |
| Zwei native Kroko-Builds sind teuer | Im Hintergrund und für beide Varianten ausführen; eine nicht erreichte Variante wird als konkrete Grenze berichtet, nicht vorgetäuscht. |
| Schemawechsel des RC-Manifests | `SCHEMA_VERSION` auf 2 erhöhen und alle Erzeuger, Verbraucher und Tests im selben Commit anpassen; es existiert noch kein veröffentlichtes Manifest. |
| Ubuntu-Regression benötigt natives ext4 | Etablierten WSL2-ext4-Weg verwenden und ein Hindernis ehrlich berichten. |

## 8. Abnahmekriterien

1. Eine kanonische Zustands-/Operationsgraph-Autorität für Trockenlauf, echte
   Veröffentlichung und Wiederaufnahme.
2. Tag vor der ersten öffentlichen Veröffentlichung, GitHub Release zuletzt.
3. Docker Hub vor GHCR, GHCR per Digest-Promotion desselben Manifests.
4. Aliase erst nach verifizierten exakten Artefakten in beiden Registries,
   danach selbst verifiziert.
5. Frischer Runner ohne Operator-lokale Abhängigkeiten; Nachweis über einen
   echten Build mit leerem Artefaktspeicher.
6. Normale CI kann nichts veröffentlichen; Veröffentlichung nur über
   ausdrückliche Freigabe.
7. README vollständig neu; `docs/engines/` entfernt; `docs/faster-whisper.md`
   und `docs/kroko-onnx.md` vorhanden; keine gepflegten Links auf
   `docs/engines/...`.
8. Vollständige Unit- und Regressionssuiten grün.
