# 4. Bereits bestätigter Fehler

Der Fehler ist **bekannt und reproduziert**. Nicht erneut grundsätzlich untersuchen.

AP-SRV-040 vergibt `eventSeq` intern korrekt monoton, aber zwei parallele Domainthreads können Events in anderer Reihenfolge an den WebSocket-Outbound übergeben.

Aktueller Ablauf sinngemäß:

```text
Thread A:
  projector.project(...)
  mint eventSeq=9
  [wird unterbrochen]

Thread B:
  projector.project(...)
  mint eventSeq=10
  self.send(10)
  sink -> loop.call_soon_threadsafe(outbound.put_nowait, 10)

Thread A:
  self.send(9)
  sink -> loop.call_soon_threadsafe(outbound.put_nowait, 9)

beobachtbar:
8, 10, 9, 11
```

Die relevante bestehende Stelle ist in `ProtocolV2Connection._on_domain_event()` sinngemäß:

```python
context = self._projection_context()
for event in projector.project(legacy_event, payload, context):
    self.send(event)
```

`projector.project(...)` mintet bereits `eventId`, `eventSeq` und `stateVersion`.

`ProtocolV2Connection.send()` holt anschließend den Sink und ruft ihn außerhalb seines normalen Connection-Locks auf.

Der `/ws/v2`-Sink macht sinngemäß:

```python
loop.call_soon_threadsafe(outbound.put_nowait, payload)
```

**Das Race liegt zwischen Event-Mint und Outbound-Enqueue.**

# 5. Verbindliche Contract-Regel

Für zwei v2-Events derselben Session gilt:

```text
E1.eventSeq < E2.eventSeq
```

muss bedeuten:

```text
E1 wird vor E2 an die Outbound-Queue / Sink-Grenze übergeben.
```

Der Client darf `eventSeq` für Deduplizierung und Gap-Erkennung verwenden. Er soll kein normales serverseitiges Reordering wie

```text
8, 10, 9, 11
```

kompensieren müssen.

Ziel:

```text
8, 9, 10, 11
```

# 6. Gewünschte kleine Lösung

Führe **eine sessionlokale Event-Dispatch-Linearisierungsgrenze** ein.

Bevorzugtes Muster:

```python
with self._event_dispatch_lock:
    context = self._projection_context()
    events = projector.project(...)
    for event in events:
        self.send(event)
```

Der konkrete Aufbau darf angepasst werden.

Wesentlich:

### Der Lock MUSS umfassen

```text
Projection / mint_event
+
Übergabe an Connection.send / Sink
```

Nicht nur `send()` locken.

Nur:

```python
with lock:
    self.send(event)
```

wäre falsch, weil `9` und `10` dann bereits außerhalb des Locks gemintet sein könnten.

- sessionlokal;
- bevorzugt `threading.RLock` oder passender einfacher Lock;
- kein `await` darunter;
- endet spätestens nach thread-safe Sink-/Queue-Übergabe;
- wartet nicht auf `websocket.send_text()`;
- darf keine neue Domain-/Ledger-/Activation-Lockordnung erzeugen.

Der asynchrone Writer bleibt unverändert:

```text

-> Event-Dispatch-Lock frei
-> writer_task sendet später
```

Kein `sleep()`.
