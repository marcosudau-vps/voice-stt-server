## Negativtests Handshake

`hello` als erste Nachricht erzwungen; ungültiges JSON, falscher erster Typ,
fehlende Pflichtfelder, leere `supportedProtocolVersions`, keine gemeinsame
Version, ungültige Sessionanforderung, unbekannte Wake-Word-ID, Audio vor
`hello.accepted`, Command vor `hello.accepted`, Handshake-Timeout und ein
unerwarteter Admissionfehler.

Close-Codes gegen die frozen Tabelle geprüft:

```text
4400  ungültige erste Nachricht / nicht parsebares Handshake / Audio vor hello
4406  keine gemeinsame Protokollversion
4408  Handshake-Timeout
4409  Sessionadmission abgelehnt
1011  unerwarteter interner Serverfehler
```

In jedem Ablehnungsfall entsteht keine `sessionId`, keine Session im
Sessionstore und kein Recorder.

## Negativtests Commands

`source=wake_word` vom Client, `activate` mit `activationId`, Control ohne
`activationId`, Control mit `source`, `extend`-Alias, fremde `sessionId`,
fremde `activationId`, gleicher `commandId` mit anderem Payload, ungültiger
Payload je Commandtyp, `activate` bei `audioAvailable=false`, unterdrückter
Trigger, nicht-kanonische `commandId` (kein Ack), unbekannter Nachrichtentyp
(ignoriert), falsche `protocolVersion`.

Ein fachlich abgelehnter Command schließt die Session nie.

## Event- und Versionstests

- `eventSeq` streng monoton und lückenlos, auch unter acht parallel mintenden
  Threads (`160` Events, `1..160` ohne Lücke);
- `eventId` kanonisch und je logischem Ereignis einmalig;
- ein Transport-Retry desselben logischen Ereignisses liefert dieselbe
  `eventId`/`eventSeq`/`stateVersion` und erhöht nichts;
- `stateVersion` steigt nicht bei `watchdog.warning` und
  `activation.trigger_suppressed`;
- `no_change` erzeugt keine neue sichtbare Version;
- Snapshot `lastEventSeq`/`stateVersion` stimmen mit dem letzten Event überein.

## Exactly-once Input-Close

| Auslöser | Ergebnis |
|---|---|
| `finish` | genau ein `activation.input_closed`, `causedByCommandId` = Command |
| `cancel` | genau ein `activation.input_closed`, `causedByCommandId` = Command |
| `audioAvailable=false` | genau ein Ereignis, `causedByCommandId = null` |
| Timer/VAD (Projektion) | `causedByCommandId = null` |
| Recovery (Seam) | `causedByCommandId = null`, obwohl der interne `CloseContext` die ursprüngliche Command-ID behält |

Zusätzlich: eine wiederholte Registrierung derselben Activation liefert
denselben Schlüssel und legt keinen zweiten Datensatz an; ein wiederholtes
`finish`/`cancel` erzeugt kein zweites Ereignis.

## Snapshot- und Resynctests

`idle`, `waiting_first_speech`, `segment_active`, `followup_wait`,
`closing_input`, `idle + 0 pending`, `idle + 1 pending`,
`idle + mehrere pending`, `offene Activation + ältere pending`,
`audioAvailable=false`, manual/wake/beide unterdrückt.
`pendingActivations` ist streng nach `activationSequence` sortiert und enthält
die offene Vordergrund-Activation nicht. Ein wiederholter
`session.snapshot.request` ändert `stateVersion` nicht.

## Race-Wiederholung

`tests/unit/test_protocol_v2_races.py`, jede Invariante 20x, Ordnung über
`threading.Barrier`/`Event`, Timeouts nur als Failsafe:

- acht Threads publizieren dasselbe logische Close-Ereignis → eine Identität;
- sechs Threads minten 90 gemischte Events → lückenlose Sequenz;
- fünf gleichzeitige Replays eines `activate` → ein Effekt, identische Acks;
- konkurrierendes `finish`/`cancel` → genau ein `applied`, genau ein
  `activation.input_closed`, korrekte Korrelation;
- Snapshot während des Backgrounddrains → konsistent und sortiert;
- Sessionclose gegen späten Timer → keine neue Domainmutation.
