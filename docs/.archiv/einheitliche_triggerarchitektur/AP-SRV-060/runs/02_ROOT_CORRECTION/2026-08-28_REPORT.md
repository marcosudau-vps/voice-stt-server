### F2 — `next_activation` wirkte nicht auf den Detector — **geschlossen**

Neu: `WakeRuntimePolicy` (sensitivity, cooldownMs, preRollMs,
settingsRevision) – unveränderlich, exakt analog zur bestehenden
`ActivationTimingPolicy`. Der `WakeDetectionEvaluator` bekommt keinen
kopierten Wert mehr, sondern einen `policy_supplier`, der auf die **eine**
AP-SRV-050-Autorität zeigt (`SessionSettingsState.activation_admission_settings()`).

Bindungsregel: solange eine Detection gelatcht ist, bleibt die Policy
eingefroren; ist der Evaluator nicht gelatcht, liest er bei jedem `offer()`,
`refuse()` und `release_latch()` die aktuelle Policy. Damit gilt
`next_activation` real – für Schwelle, Cooldown **und** Pre-Roll; die
Audiogrenze zieht ihren Pre-Roll aus derselben gelatchten Policy statt aus
einem beim Sessionaufbau kopierten Recorderattribut.

Keine zweite Settingsautorität, keine Änderung an einer laufenden Activation.

### F3 — „unloadable" wurde vor der Admission nicht validiert — **geschlossen**

`admit_selection` erhält eine echte Ladbarkeitsprobe. Default ist eine
`onnxruntime.InferenceSession` auf genau der Datei – dieselbe Operation, die
OpenWakeWord beim Laden ausführt. Eigenschaften:

- nur die **ausgewählten** Klassifikatoren plus die zwei gemeinsamen
  Pipelinemodelle werden geprüft – selected-only bleibt intakt;
- das Ergebnis ist je Artefaktidentität (Pfad, Größe, mtime) memoisiert; ein
  Reload verwirft den Cache;
- die Probesession wird sofort verworfen – es entsteht keine zweite dauerhafte
  Modellinstanzfamilie;
- Klassifikatoren werden vor der Pipeline geprüft, damit die spezifischste
  Ursache gewinnt;
- fehlt eine ONNX-Runtime vollständig, wird nicht geprobt statt pauschal
  abgelehnt.

Fehlerpayload: `field`, `code = wake_word_unavailable`, `wakeWordId`,
`reason = artifact_unloadable`, nicht geheime `message` (der Runtimefehlertext
wird nicht durchgereicht). Eine abgelehnte Session erzeugt weder `sessionId`
noch Recorder – im Test nachgewiesen.

### F4 — Detection-Sample galt als bewiesene Wake-Endgrenze — **geschlossen**

`WakeAudioBoundary` benennt jetzt, was gemessen ist und was nicht:

```text
detection_sample                gemessen
receptive_field_start_sample    gemessen
estimated_wake_end_sample       Schätzung  (derzeit == detection_sample)
release_sample                  berechnet
boundary_basis                  "detection_sample_estimate"
```

ausdrücklich, dass die Grenze eine konservative Schätzung ist und WW-19

### F6 — Rearm erzeugte einen versteckten zweiten Lock — **geschlossen**

Aus einem Fenster wurden zwei mit klar getrennter Semantik:

| | Entprellfenster | Cooldown |
|---|---|---|
| Herkunft | implizit, gemessenes Empfangsfenster | explizit konfiguriert |
| Zweck | denselben akustischen Treffer nicht zweimal anbieten | bewusste Betreiberpause |
| safe input close | **wird gelöscht** | bleibt bestehen |

`release_latch()` löscht das Entprellfenster; zusätzlich löscht
`WakeAdmissionCoordinator.release()` es auch dann, wenn gar kein Latch bestand
(abgelehnter Treffer gefolgt von einem sicheren Close). Ein alter Treffer kann
damit keinen neuen legitimen Wake-Trigger mehr blockieren. Der konfigurierte
Cooldown überlebt bewusst und ist als solche Semantik dokumentiert.

### F7 — Fault nach Activation-Commit — **geschlossen**

Eingeführt: `WakeActivationOutcome(committed, activation_id, error)`.
`ActivationController.activate` ist der Commitpunkt.

```text
vor dem Commit   Guard, Refusal, Settingsfehler  -> keine Activation, Refusal
nach dem Commit  Decision-Anwendung, Eventsammlung, Eventpublikation,
                 wakeword.detected-Publikation   -> niemals Refusal
```

`_activate_from_wake_candidate` fängt seine Post-Commit-Fehler selbst, meldet
sie über `outcome.error` und wirft nach dem Commit nicht mehr. Der Coordinator
umschließt keine mutierende Operation mehr mit „catch → None".

Zusätzlich strukturell abgesichert: wirft der Admissionpfad trotzdem, fragt der
Coordinator über `committed_probe` die Activation-Autorität, ob eine
Wake-Activation offen ist. Ist sie es, wird der Fall als Post-Commit-Fehler
behandelt statt als Refusal. Eine committete Activation ohne Latch kann so
nicht mehr entstehen. Eine fehlgeschlagene `wakeword.detected`-Publikation
lässt Activation, Latch und akzeptierte Detection unangetastet.

### F8 — Revision konnte ohne Event steigen — **geschlossen**

Der Defekt lag im Serviceadapter: `_on_wake_word_availability_changed`
verwarf jede Meldung mit `if not availability_changed: return`. Der Adapter
heißt jetzt `_on_wake_word_catalog_changed`, hat keinen Guard mehr und
veröffentlicht **jede** sichtbare Katalogänderung mit der neuen
`catalogRevision` und den aktuellen `availableWakeWordIds`. Der eingefrorene
Eventname `wakeword.availability_changed` bleibt – der Frozen Contract sieht
ihn als Catalog-Change-Seam vor; die breitere Semantik ist in Produkt- und
Clientdoku ausdrücklich beschrieben. Es entsteht keine neue Eventfamilie.

### F9 — öffentlicher Entry ohne `catalogRevision` — **geschlossen**

`WakeWordCatalogSnapshot.public_catalog()` ergänzt jeden Eintrag um die
Revision des Snapshots, aus dem er stammt; die Top-Level-Revision bleibt
zusätzlich bestehen. Wichtig für die Regressionsfreiheit:
`visible_projection()` vergleicht bewusst die **revisionsfreie**
Eintragsprojektion – sonst würde jeder Refresh die Revision erhöhen. Ein
eigener Test sichert das ab.

### F10 — Refreshantwort konnte zwei Zustände mischen — **geschlossen**

Drei Änderungen:

1. `WakeWordCatalogAuthority.refresh(global_disabled_ids=…)` wendet Reload und
   Disable-Projektion in **einer** gelockten Operation an; der frühere zweite
   `set_global_disabled`-Aufruf im Service entfällt.
2. `RefreshResult` trägt den committeten `snapshot` und liefert
   `public_payload()` – eine atomare Projektion aus genau diesem Snapshot.
3. Der HTTP-Handler rendert ausschließlich daraus und liest die Autorität nicht
   mehr ein zweites Mal.

Auch `GET /api/v2/wake-words` liest nur einen Snapshot. Damit stammen
Top-Level-Revision, Eintragsrevisionen, `available` und
`availableWakeWordIds` einer Antwort immer aus einem logisch konsistenten
Zustand. Vier Racetests (je 20 Runden, `Barrier`) belegen das.

## Hinweise für Root

1. **Neuer Rejectgrund `not_canonical`** (additiv neben dem eingefrorenen
   `code = wake_word_unavailable`). Falls Root einen anderen Grundnamen
   vorzieht, ist das eine Einzeiländerung an einer Stelle.
2. **`wakeword.availability_changed` ist jetzt bewusst breiter als sein Name.**
   Der Frozen Contract führt genau dieses Event als Catalog-Change-Seam; es
   wurde keine neue Eventfamilie erfunden. Falls Root stattdessen einen zweiten
   Eventnamen will, wäre das eine Contractänderung.
3. **Die Ladbarkeitsprobe kostet einmalig eine `InferenceSession` pro
   Artefakt.** Auf dieser Maschine liegt das im Millisekundenbereich und ist
   memoisiert; auf sehr schwacher Hardware wäre die erste Admission je Modell
   entsprechend langsamer.
4. **`available` im öffentlichen Katalog bleibt existenz- und pipelinebasiert.**
   Die Ladbarkeit wird bei der Admission geprüft, nicht bei jedem Refresh über
   alle 26 Modelle. Falls Root `available` truthful gegen die Probe haben will,
   ist das ein bewusster zusätzlicher Refreshaufwand.
5. **WW-18/WW-19 bleiben der einzige Abnahmeblocker.** Sie sind kein
   Codedefekt, sondern eine fehlende externe Voraussetzung.
