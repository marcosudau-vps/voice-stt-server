## F1 — v2-Wire akzeptiert fälschlich Aliase / Display Names

### Verletzte Invariante

`requestedSession.wakeWordIds` im v2-Hello enthält **kanonische IDs**.

Tolerante Human-Auflösung für:
- `jarvis`
- `Hey Jarvis`
- Separatorvarianten

ist für menschliche Konfiguration zulässig, aber NICHT für das v2-Wire.

### C1-Fehler

Der v2-Handshake verwendet denselben toleranten Resolver wie Human Config.

Die neuen C1-Tests schreiben sogar das falsche Verhalten fest:

```text
"jarvis"     → accepted
"Hey Jarvis" → accepted
```

### C2-Anforderung

Trenne klar:

```text
Human/config resolver:
tolerant, explizite Aliase, Display Names

v2 wire admission:
canonical IDs only
```

Eine nicht-kanonische Wire-ID muss die gesamte Session als
`session.rejected` ablehnen.

### RED-/Regressiontests

Mindestens:

```text
hey_jarvis  → ACCEPT
jarvis      → REJECT
Hey Jarvis  → REJECT
HEY-JARVIS  → REJECT
unknown     → REJECT
```

Human-Resolver-Tests müssen weiterhin zeigen, dass explizite Aliase außerhalb
des Wire-Kontexts korrekt funktionieren.

## F2 — `next_activation` Wake-Settings wirken nicht real auf den Detector

### Verletzte Invariante

```text
wakeWord.sensitivity
wakeWord.cooldownMs
wakeWord.preRollMs
```

sind `next_activation`.

Ein akzeptierter Session-Settings-Patch muss deshalb spätestens für die
**nächste Activation** real in der Wake-Runtime wirken.

Eine laufende Activation bleibt gelatcht/frozen.

### C1-Fehler

`WakeDetectionEvaluator` und Recorder-Pre-Roll werden beim Sessionaufbau einmal
mit den damaligen Werten gebaut.

Ein späterer Patch ändert `SessionSettingsState`, aber nicht die reale
Detector-/Boundary-Konfiguration.

### C2-Anforderung

Baue eine eindeutige, race-sichere Bindung der AP-SRV-050 Settings Authority an
die Wake-Runtime.

Keine zweite Settingsauthority.

Erlaubte Architektur:

- immutable per-Activation Wake Runtime Policy;
- oder atomarer Rebind unmittelbar vor einer neuen Wake-Admission/Activation;
- oder gleichwertige Lösung.

Nicht:
- laufende Activation nachträglich verändern;
- Detectorwerte still aus einer zweiten Registry lesen.

### Pflichtnachweise

Deterministische Tests:

1. Session startet sensitivity A.
2. Patch auf B.
3. laufende Activation bleibt A.
4. nächste Wake-Activation verwendet B real.

Dasselbe für:
- cooldown;
- preRoll.

Tests dürfen nicht nur Wire-/Schemawerte prüfen, sondern müssen reale
Evaluator-/Boundary-Werte beobachten.

## F6 — Rearm kann nach Safe Input Close einen versteckten zweiten Lock erzeugen

### Verletzte Invariante

Der Wake-Latch endet am **safe input close**.

Detector-Hygiene darf keine zweite Vordergrundsperre erzeugen, die das
Activation-Lifecycle-Modell heimlich erweitert.

### C1-Fehler

Bei Accept/Refusal wird:

```text
blocked_until = now + rearm + cooldown
```

gesetzt.

`release_latch()` löscht aber nur den Latch, nicht `blocked_until`.

Damit kann nach Safe Input Close weiterhin mehrere Sekunden kein neuer Wake-Hit
angenommen werden.

### C2-Anforderung

Definiere und dokumentiere sauber:

```text
Latch
Rearm
Cooldown
Safe input close
```

Der Basisschutz gegen denselben akustischen Hit darf nicht als unbeabsichtigter
sessionweiter Foreground-Lock fortleben.

Insbesondere:
- wenn Input geschlossen und neue Activation zulässig ist, darf ein alter
  accepted hit nicht allein wegen des alten Receptive-Field-Rearmfensters einen
  neuen legitimen Wake-Trigger blockieren;
- falls ein **explizit konfigurierter** Cooldown später nach Evidence eine
  Nachsperre bilden soll, muss das bewusst definierte Semantik sein und darf
  nicht aus Receptive Field "nebenbei" entstehen.

### Tests

Deterministisch:
- accept;
- unmittelbar safe close;
- neuer klar separater Hit;
- darf nicht durch alten hidden rearm blockiert sein.

Zusätzlich Refusal-Fall prüfen.

## F7 — Fault nach Activation-Commit kann zu offener Activation ohne Wake-Latch führen

### Verletzte Invariante

Ein akzeptierter Wake-Hit muss logisch atomar ergeben:

```text
Activation accepted
+ AcceptedWakeDetection
+ Latch
+ genau ein wakeword.detected
```

Ein Fehler nach realem Activation-Commit darf nicht so behandelt werden, als
wäre die Wake-Admission einfach rejected worden.

### C1-Fehler

`WakeAdmissionCoordinator.admit()` fängt jede Exception aus `_activate()` und
wandelt sie in Refusal um.

`_activate_from_wake_candidate()` hat zu diesem Zeitpunkt potentiell bereits:
- ActivationController erfolgreich mutiert;
- Activation-Entscheidung angewandt;
- interne Events gesammelt;
- danach kann Eventpublikation werfen.

Dann:

```text
Activation offen
Wake evaluator refused/unlatched
kein konsistentes AcceptedWakeDetection
```

Zusätzlich kann die `wakeword.detected`-Publikation selbst nach Latch werfen.

### C2-Anforderung

Definiere eine echte Commit-/Fault-Grenze.

Root erwartet strukturell:

```text
pre-commit failures → keine Activation
post-commit failures → bestehende Activation darf nicht als Refusal behandelt werden
```

Kein "catch Exception → None" um eine bereits mutierende Operation.

### Pflicht-Fault-Injection-Tests

Mindestens:

1. Activation admission selbst wirft vor Commit.
2. Event collection/projection wirft vor Commit.
3. Publish der Activationevents wirft nach Commit.
4. `wakeword.detected` publish wirft nach AcceptedWakeDetection/Latch.
5. Session close konkurriert mit accepted wake admission.

Für jeden Fall:
- Activationzustand;
- Latchzustand;
- Eventanzahl;
- kein Source-Merge;
- keine zweite Activation;
- keine stale Wirkung.

Event bereits als Catalog-Change-Seam vorsieht.

### Tests

- keine sichtbare Änderung → keine revision++, kein Event;
- Availabilityänderung → revision++ und Event;
- failed refresh → keine revision++, kein Event, last-known-good bleibt.

```text
READY FOR ROOT REVIEW
```

mit:
- C2 SHA;
- Tree;
- Parent;
- clean status;
- Tests;
- Race counts;
- Evidence.

## B — Codefindings geschlossen, aber positive WW-18/WW-19 Evidence fehlt

Dann:

```text
EVIDENCE_BLOCKED
```

mit:
- C2 SHA;
- Tree;
- Parent;
- clean status;
- F1–F10 = geschlossen;
- exakter verbleibender Evidencebedarf;
- keine falsche PASS-Aussage.

Auch bei `EVIDENCE_BLOCKED` darf der lokale C2-Commit erstellt werden, sofern
die Codekorrekturen in sich vollständig und grün sind.

Dann stoppen.
