# 2. GIT-MODELL UND ISOLIERTER C1-WORKTREE

Für dieses Projekt gelten drei klar getrennte Ebenen:

```text
feat/einheitliche-triggerarchitektur
    = kanonische Linie
    = genau ein Gesamt-Commit je vollständig Root-abgenommenem Arbeitspaket

feat/einheitliche-triggerarchitektur-distributed
    = Ausführungs-/Reviewlinie
    = genau ein eigener Commit je für Root Review eingereichtem Agenten-Run
    = C1 → C2 → C3 ... bauen innerhalb des Arbeitspakets aufeinander auf

weitere branches/workspaces
    = temporäre/isolationstechnische Arbeitsbereiche
    = dürfen nach Bedarf benutzt werden
    = sind weder canonical noch distributed authority
```

Wichtig für diesen C1-Lauf:

- Du veränderst den kanonischen Branch nicht.
- Du reparierst, resettest, rebased oder force-updatest den Distributed-Branch nicht.
- Du pushst nichts.
- Du erzeugst einen sauberen lokalen **C1-Run-Commit** exakt auf der unten gepinnten kanonischen AP-SRV-050-Basis.
- Root/Koordination übernimmt anschließend die Einordnung/Publikation dieses C1-Run-Commits in die Distributed-Reviewlinie.
- Sobald C1 als `READY FOR ROOT REVIEW` abgegeben wurde, gilt dieser eingereichte C1-Stand als unveränderliche Run-Provenienz.
- Falls Root Befunde zurückgibt, entsteht daraus ein **neuer C2-Commit auf C1**, später ggf. C3 usw. C1 wird nach Einreichung nicht weg-amended.

Der aktuell auf GitHub sichtbare Distributed-Branch kann historisch hinter dem kanonischen Stand liegen. Das ist **kein Auftrag an dich**, ihn eigenmächtig zu synchronisieren. Die Koordination behandelt diese Git-Referenz.

# 8. TOLERANTE MENSCHLICHE NAMENSAUFLÖSUNG

Es gibt genau einen Resolver.

Für menschlich editierte Konfigurationswerte:

1. Unicode normalisieren;
2. außen trimmen;
3. casefold/case-insensitive vergleichen;
4. Trennzeichen zwischen Wortbestandteilen deterministisch vereinheitlichen;
5. nur gegen kanonische IDs, Anzeigenamen und explizite Aliase auflösen.

Diese Formen sollen z. B. auf dieselbe explizite ID auflösbar sein:

```text
hey_jarvis
Hey Jarvis
HEY-JARVIS
hey.jarvis
hey__jarvis
```

Wichtig:
Der Frozen Contract verbietet heuristisches Entfernen von „Hey“.

Darum gilt:

```text
jarvis → hey_jarvis
```

nur, wenn `jarvis` explizit als Alias dieses Modells im Manifest steht.

Dasselbe Prinzip für andere Wake Words.

Nach Normalisierung:
- ID↔ID;
- Alias↔Alias;
- Alias↔ID

müssen kollisionsfrei sein.

Keine Reihenfolge, kein Dateiname, kein fuzzy/best match entscheidet Kollisionen.

Der strikte v2-Handschlag bleibt kanonisch:
`requestedSession.wakeWordIds` sind kanonische IDs.

# 16. WAKE ADMISSION UND LATCH

Der Wake-Latch gehört nicht in den `ActivationController`.

AP-SRV-010/030 bleiben gemeinsame source-neutrale Activation Authority.

Pfad:

```text
Raw Candidate
→ Detection Evaluation
→ Wake Admission Coordinator
→ ActivationController.activate(source="wake_word")
```

Nur wenn Activation Admission erfolgreich ist:

- Detection fachlich accepted;
- Wake-Latch setzen;
- akzeptierte `activationId` übernehmen;
- genau ein `wakeword.detected`.

Wireevent:

```text
activationId
wakeWordId
score
primarySource = wake_word
```

Bei `activation_locked`, Suppression oder anderer Ablehnung:
- kein `wakeword.detected`;
- kein neuer fachlicher Latch;
- keine zweite Activation;
- kein Source-Merge.

Latch bis zum sicheren Eingabeschluss derselben Activation.

Nicht bis:
- VAD-Ende;
- Segmentende;
- Start/Ende Final-Inferenz;
- Cooldownablauf.

Wake Word während offener Activation besitzt keinerlei direkte Trigger-/Finish-/Cancel-/Refresh-Wirkung.
