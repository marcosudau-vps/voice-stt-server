## 7. Test selbst prüfen

Der Test verwendet sinngemäß:

```python
original_close = server.close

def observed_close():
    try:
        return original_close()
    finally:
        terminated.set()

server.close = observed_close
```

Dann:

```python
terminated.wait()
assert server.status == "closed"
```

Beweise:
- Wer ruft `server.close()` tatsächlich auf?
- Auf welchem Thread?
- Gibt es einen zweiten Lifecycle-/Context-Manager-Pfad?
- Kann `ControlledSessionHarness` nach `terminated.set()` selbst Status-/Cleanup-Operationen ausführen?
- Ist `terminated` der richtige Linearization Point?
- Wird `close()` mehrfach oder rekursiv aufgerufen?
- Ist `server` dieselbe Sessioninstanz, deren Status beobachtet wird?

Test nur korrigieren, wenn der tatsächliche Lifecycle das eindeutig belegt. Nicht lockern, nur damit er grün wird.

## 8. Recovery-/Timerpfad vollständig prüfen

Besonders verdächtig:

- Was macht `_activation_timer_worker()` **nach** `_publish_collected_events()`?
- Setzt/publiziert er danach noch `waiting_state`?
- Wird `waiting_state` vor dem Recovery berechnet und später veröffentlicht?
- Kann dadurch nach terminalem `close()` wieder `listening` gesetzt werden?

Wenn der reale Ablauf etwa ist:

```text

→ waiting_state vorbereiten
→ publish collected events
    → recovery
        → session close
→ danach publish_status(waiting_state)
```

ist das die Root Cause. Dann muss der Fix am Worker-/Lifecycle-Vertrag sitzen, nicht in weiteren Status-Seals.
