5. VERBINDLICHE TIMERSEMANTIK
======================================================================

Intern ausschließlich monotone Zeit für Ablaufentscheidungen verwenden.

--------------------------------------
Initial Speech
--------------------------------------

Default:
15000 ms

Nach Activation-Admission:
deadline = now + initialSpeechTimeout

Refresh in waiting_first_speech:
UNZULÄSSIG / invalid_phase.

--------------------------------------
Follow-up
--------------------------------------

Default:
3000 ms

Nach regulärem Segmentende:
deadline = now + followupTimeout

Refresh in followup_wait:

deadline = now + followupTimeout

WICHTIG:

KEIN extensionSeconds.
KEIN pending_extension.
KEIN Zeitguthaben.
KEINE Akkumulation.

Dreimal Refresh bedeutet dreimal „ab jetzt neu setzen“,
nicht dreimal zusätzliche Zeit.

--------------------------------------
Segment Watchdog
--------------------------------------

Initialdefault:
600000 ms / 600 Sekunden

Beim Start eines aktiven Segments:

deadline = now + segmentWatchdogInitialMs

Refresh während segment_active:

deadline =
max(
    currentDeadline,
    now + segmentWatchdogRefreshMs
)

Default segmentWatchdogRefreshMs:
180000 ms / 180 Sekunden

Damit gilt ausdrücklich:

- früher Refresh darf eine noch längere Restfrist NICHT verkürzen;
- später Refresh sichert mindestens 180 Sekunden ab Interaktion;
- Refresh kumuliert keine Zeit.

VAD-Aktivität setzt den Watchdog NICHT zurück.

Warning:
standardmäßig 30000 ms vor Ablauf.

Watchdog-Ablauf:

- bereits erfasstes Audio regulär verarbeiten;
- gesamte Activation schließen;
- KEIN Follow-up öffnen;
- Vordergrund nach sicherem Input-Close wieder freigeben.

--------------------------------------
Closing Recovery
--------------------------------------

closing_input darf niemals unbegrenzt hängen.

Default Recoverytimeout:
5000 ms

Stale Recoverytimer oder Timer einer älteren Activation dürfen keine neuere
Activation verändern.

6. TIMERREVISION UND STALE-SCHUTZ
======================================================================

Jede wirksame Timeränderung muss eine neue timerRevision besitzen.

Timer-Callbacks müssen mindestens gegen die Identität prüfen, die notwendig
ist, damit ein alter Callback niemals einen neueren Zustand verändern kann.

Insbesondere berücksichtigen:

- Activation-ID;
- Activation-Generation/Sequence;
- timerRevision;
- aktuelle Phase;
- ggf. Segmentidentität für Segment-Watchdog.

Ein stale Callback ist wirkungslos.

Wallclock-Sprünge dürfen Ablaufentscheidungen nicht beeinflussen.

Wire-Darstellungszeitpunkte aus SRV-040 nicht vorwegnehmen.

--------------------------------------
refresh
--------------------------------------

waiting_first_speech:
invalid_phase

segment_active:
Watchdog-Refresh nach oben definierter max()-Semantik

followup_wait:
Follow-up-Deadline = now + followupTimeout

closing_input:
closing_input / keine neue Wirkung

idle:
not_active

--------------------------------------
finish / cancel
--------------------------------------

In jeder offenen Phase zulässig:

- waiting_first_speech
- segment_active
- followup_wait

Sie müssen die beobachtete aktuelle activationId validieren.

Eine alte/falsche Activation-ID:
stale_activation
und keinerlei Zustandsänderung.

In closing_input:
idempotente Zustandsantwort / keine zweite Transition.

Finish:
angenommene Segmente regulär weiterverarbeiten.

Cancel:
nur noch NICHT veröffentlichte Resultate unterdrücken.
Bereits veröffentlichter Text wird niemals zurückgenommen.

Genau ein fachlicher Input-Close-/Lifecycle-Vorgang pro neu angenommener
Transition.

Das endgültige öffentliche Eventformat gehört zu SRV-040.

======================================================================
8. COMMAND-ID REPLAY
======================================================================

Führe eine sessiongebundene Idempotenz-/Replaylogik ein.

Für jedes logische Command wird commandId berücksichtigt.

Gleiche commandId + semantisch identischer Payload:

- dieselbe ursprüngliche Antwort;
- keine zweite Wirkung;
- keine zweite Transition;
- kein zweiter Timerreset;
- kein zweites Cancel/Finish;
- keine neue Activation.

Gleiche commandId + anderer Payload:

command_id_conflict

Der Replaycache gilt mindestens für die gesamte Session.

Der Cache darf nicht dazu führen, dass stale Commands gegen eine neuere
Activation erneut wirksam werden.

Design sauber vom späteren Wire-v2-Parser trennen.

======================================================================
9. AUDIOVERFÜGBARKEIT UND RECOVERY
======================================================================

Generisches:

audioAvailable=false

muss bei einer offenen Activation zu einem kontrollierten Cancel führen,
ohne die gesamte Serversession zu beenden.

Die Geräte-/ReSpeaker-Logik selbst ist Clientverantwortung und gehört NICHT
in dieses AP.

Server-/Sessionverlust:
laufende Activation wird verworfen;
keine Fortsetzung in einer neuen Session.

Gate-/Recorderfehler während closing_input dürfen den Vordergrund nicht
dauerhaft blockieren.

Recovery muss:

- den Inputpfad defensiv schließen;
- bereits angenommene Ledgersegmente korrekt terminalisieren bzw. weiterführen;
- keine bereits publizierten Resultate zurücknehmen;
- stale Recoveryaktionen isolieren;
- einen definierten Rückweg nach idle besitzen.

AP-SRV-020-Ledgerinvarianten müssen vollständig erhalten bleiben.
