## 1. Worum geht es?

Kein Benutzerkonto, keine Rolle, kein Mandant (N1). Kein Ausweis „Ich bin Session X" (N3). Trennung ist technisch, nicht Rechte. Vier Formen statt RBAC: (a) Scope – welches Feld über welchen Weg; (b) Token-Bindung – zu welcher Session gehört ein Log-Token; (c) ID-Gleichheit – passt Kommando-ID zur Verbindung; (d) konstruktive Trennung – gibt es überhaupt ein Adressfeld. 401 ≠ stale_session; 200-leer ≠ nicht vorhanden.

| Begriff | Bedeutung |

| Session | Technische Einheit einer V2-Verbindung; ID vergibt der Server (E2-13). |

## 3. Settings-Scope (E2-02..E2-06)

Prüfung feldweise atomar: Session-Patch server-Key → wrong_scope; writable=False → `read_only_runtime_authority`; Server-Patch ohne has_server_default → wrong_scope (E2-03). ## 4. Token-Bindung (E2-07..E2-11)

Genau eine sessionId; validate None bei Abweichung; 64 Hex, 24 h, flüchtig, kein Revoke (E2-07). HTTP: fremde ID → 401 (Code, ungetestet-Teil); Admin/Loopback-Regeln separat; Nicht-Admin Kanäle beschnitten sonst 200 (E2-08). WS: gleiche Bindung, kein Loopback-Admin; None → not_authorized + 1008 (E2-09). Ausgabe nur Bootstrap (v1-hello, v2-hello.accepted) bei live+Store, sonst available=false; nicht im Resync (E2-10). Kein Revoke: bis Ablauf nutzbar – ID-Bindung, nicht Lebensdauer (E2-11, C1). 401 (Session-Grenze) vs 200-leer (Datensatz-Grenze bei fremder transcriptionId) unterscheiden (E2-08/E2-16).
